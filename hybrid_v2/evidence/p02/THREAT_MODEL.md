# P02 threat model: what is authenticated, against whom, and what is NOT

| Asset / claim | Adversary or failure | Control | Residual risk (honest) |
|---|---|---|---|
| Human approval (story, direction, design, art, states, edges, shot, unlike, film) | A typed TTY confirmation, a hand-written receipt, a replayed, wrong-scope, stale or expired envelope, a diagnostic key, or a revoked approval | An ed25519 envelope verified against `ART_BRIDGE_REVIEWER_KEYS_FILE` *outside the repo*, bound to scope, record, bundle hash and a single-use nonce. Revocations are tracked in the append-only `reviews/HISTORY.jsonl`. Tested in P02-R16 and P02-R16/R21. | **No production trust anchors exist yet.** Every HUMAN gate is therefore blocked (correct). Anyone holding the private key can sign: key custody is the operator's job. |
| Test authority | Test trust used on a production film; diagnostic receipts or anchors copied into a production film | Test trust requires `ART_BRIDGE_TEST_TRUST=1` **and** a `.diagnostic_namespace` marker. Diagnostic anchors are loaded only inside the namespace. `createRun` refuses mixed run types. | A person who deletes or adds the marker file changes the namespace. The production preflight still requires HUMAN receipts and GPT provenance. |
| Art provenance | `--provenance GPT_PROVIDER_ART` on an arbitrary PNG; a handoff image relabelled as API art | `requireProvenanceLineage`: the bytes must be a valid candidate of a **sealed** provider or handoff record with exactly that provenance (P02-R26). | An operator-attested ChatGPT origin is not cryptographically verified. It is recorded as `MODEL_ORIGIN_CLAIM_OPERATOR_ATTESTED` and never upgraded. |
| Paid provider calls | A blind retry after a timeout, duplicate workers, a call outside a batch, budget overrun | `REQUEST_PREPARED` is written before any send, and outcomes are typed. `OUTCOME_UNKNOWN` halts and needs operator reconciliation. A signed paid-run manifest bounds jobs, ceiling and retries (P02-R19, P02-F089). | The provider exposes no idempotency key, so a request whose outcome is truly unknown needs a human to check the provider's dashboard. **No live call was made.** |
| Capabilities | Declared `IMAGE_PROVIDER_CAPS` claiming edit, transparency, multi-reference or size support | Only a stored canary result makes a capability `LIVE_VERIFIED`. Fake outputs (opaque, wrong size, a dropped reference) are rejected (P02-R27). | No canary has been run, by design: it would be a paid call. |
| Ledger / history | Altered, deleted, reordered, duplicated, cross-linked or truncated events; a forged STATUS file; an event that only claims completion | Hash chain, HEAD pointer, store mirror and a fenced lock. Replay counts a task as complete only when its verified outputs resolve to the recorded bytes (P02-R15a–d). | An attacker with write access can rewrite the whole chain consistently. No external anchor (for example a signed checkpoint) is implemented yet. Listed in OPEN_ITEMS. |
| Stage handoffs | A forged or missing packet, or a producer changed after commit | The packet is stored by content hash, carries the producer source sha and is re-verified before the next stage starts (P02-R13; rehearsal phase C). | Same as the ledger row. |
| Renders | A CLI `--source` claim, an upscaled 16×9 MP4, a replaced MP4, a nondeterministic renderer | Only `renderFilm` receipts count. The receipt is verified by a fresh-session re-render of the boundary, final and seeded frames (P02-R04/R05, film_revision P02/P05, B3-4, P06). | Re-rendering proves reproducibility, not artistic quality. |
| Locks / selection | Two sessions racing; a crashed holder; a mistaken stale-lock steal | mkdir lease plus a fencing generation, with exclusive create on commit (P02-R20, P02-R15d). | A Windows clock or PID reuse could make a live holder look dead; the fencing check still blocks its commit. |
